# 接骨院 予約管理システム 要件定義

## 1. 目的
- 患者がスマートフォンから24時間ネット予約できるようにし、電話での予約受付の負担を減らす
- 院長が予約と営業日・営業時間を1つの管理画面で管理できるようにする
- 小規模な院で長く使い続けられるよう、過度に複雑にせず、保守しやすく理解しやすい構成にする

## 2. 技術構成
- バックエンド：PHP / Laravel
- フロントエンド：TypeScript / React / Next.js
- 開発には Claude Code を利用
- できるだけ無料または低コストで構築
- スマートフォン前提のレスポンシブデザイン
- 既存の接骨院ホームページの「ネット予約はこちら」リンクから遷移する想定
- 患者側にはログイン画面を設けない

## 3. 患者側の予約入力
- 必須：氏名（フルネーム）、電話番号、初回／再来、予約日時
- 任意：メールアドレス、施術希望内容
- メールアドレスは必須にしない（メールを使わない高齢者なども想定）
- メールアドレス欄の補足説明：「予約日時の確認や変更・キャンセルのお知らせをメールで受け取りたい場合は、メールアドレスを入力してください。」
- メールアドレスを入力した場合のみ「メールアドレス（確認）」欄を表示し、一致を確認する
- 電話番号は SMS 送信には使わない（院長が必要に応じて電話連絡するためのもの）

## 4. 予約枠・営業時間
- 予約枠は30分単位
- 平日：午前 9:00〜13:00 / 午後 16:00〜19:00
- 土曜：午前 9:00〜13:00
- 日曜・祝日：原則休診
- 水曜：第1・第3水曜は休診、第2・第4水曜は営業（初期設定）
- 曜日ごとの設定は固定値で決め打ちしない。曜日ごとの基本設定を初期値として持ち、院長がカレンダーから日付ごとに変更できる

## 5. 予約時間の表示
- 9:00〜13:00 の場合、予約開始時刻は 9:00, 9:30, …, 12:30（13:00 は含めない）
- 16:00〜19:00 の場合は 16:00, …, 18:30
- 患者側には ○ = 予約可能 / × = 予約不可 と表示する

## 6. 予約可能期間
- 現在から30日以内（「1か月」ではなく30日換算。土日祝もカウントに含める）

## 7. 同一人物の予約制限
- 同じ患者は同じ日に複数の予約ができない
- 同一人物かどうかは「氏名＋電話番号」で判定する（メールアドレスは判定に使わない）
- 別の日であれば予約できる

## 8. 二重予約の防止
- ほぼ同時に予約操作が行われても、1つの枠に複数人が予約できないようにする
- 予約確定時に DB 側でも空き状況を再確認する（画面上の ○／× 判定だけに頼らない）
- DB トランザクション等で競合を防ぎ、「先に確定した予約のみ成立する」ようにする

## 9. 予約完了画面
- 表示内容：「予約が完了しました」、予約日時、氏名、予約管理ページへのリンク
- メールアドレスを入力した場合のみ「確認メールを送信しました」と表示する

## 10. メール通知
- メールアドレスを入力した患者にだけ、予約完了後にメールを送る
- 内容：予約完了のお知らせ、氏名、予約日時、初回／再来、施術希望内容、予約管理ページへのリンク、変更・キャンセルの案内

## 11. 予約管理URL
- 患者ごとのログインは作らない
- 予約ごとに推測困難なランダムな URL を発行する（例：`/reservation/{token}`）
- 管理ページでできること：予約内容の確認、予約日時の変更、施術希望内容の変更、キャンセル
- 予約終了後は URL を無効化する

## 12. 患者側の予約変更
- 変更できるのは「予約日時」と「施術希望内容」のみ（氏名・電話番号・メールアドレス・初回／再来は変更不可）
- 予約日時の変更は予約時刻の1時間前まで
- 処理の流れ：新しい枠の空きを確認 → 新しい枠を確保 → 元の枠を空きに戻す
- 予約情報は上書き更新する（変更履歴は不要）
- メールアドレスがある場合は変更完了メールを送る

## 13. 患者側のキャンセル
- キャンセルは予約時刻の1時間前まで
- 予約データはすぐに削除せず「キャンセル済み」の状態で保存する
- メールアドレスがある場合はキャンセル完了メールを送る
- メールアドレスがない場合はオンラインで変更・キャンセルできないため、院長へ電話してもらう

## 14. 予約データの保存期間
- 予約終了後1年間保存する（キャンセル済みも同じ）
- 1年を過ぎたデータは個人情報（氏名・電話番号・メールアドレス・施術希望内容など）も含めて自動で削除する
- 毎日自動でチェックして削除する

## 15. メール送信に失敗したとき
- メール送信に失敗しても予約は成立させる（キャンセルしない）
- 院長が送信失敗を確認できるように、送信結果のログ・ステータスを DB に保存する

## 16. 院長用の管理画面：認証
- 利用者は院長1名
- シンプルなパスワード認証。パスワードは平文で保存せず、安全な方法でハッシュ化する
- ログイン失敗が続いた場合は一時的にログインを制限する

## 17. 管理画面：予約一覧
- 表示項目：予約日時、氏名、初回／再来、電話番号、メールアドレス、施術希望内容、予約状態
- 予約日時の昇順で表示する
- 検索・絞り込み：日付、氏名、電話番号、予約状態（予約中／キャンセル済み）

## 18. 管理画面：予約の操作
- 新規予約の登録、予約日時の変更、キャンセル、施術希望内容の変更、患者情報の変更
- 電話予約などではメールアドレスは任意。メールアドレスがなければ通知しない
- メールアドレスがある場合は予約管理 URL を発行してメールで通知できる

## 19. 院長側からの変更・キャンセル
- 院長が予約日時を変更したら、患者側から見える予約情報も更新する
- 院長がキャンセルしたら状態を「キャンセル済み」にする
- メールアドレスがある患者には、変更・キャンセル時にメールで通知する（ない場合は通知しない）

## 20〜24. 営業日・営業時間の管理
- 管理画面にカレンダーを表示する。曜日ごとの基本設定を初期値として持つ
- 日付を選ぶと、同じ画面内に編集エリアを展開する（別タブ・別ウィンドウにはしない）
- 通常は閲覧状態。「編集」ボタンを押したときだけ編集できる
- 編集項目：前半枠、後半枠、休診設定（初期値は前半 9:00〜13:00、後半 16:00〜19:00）
- 休診日は時間枠や時間入力欄を表示せず、「10月10日（土） 休診」のように表示する
- 日付ごとに営業時間を変更できる（例：10:00〜13:00 / 16:00〜18:00）
- 「保存」と「キャンセル」ボタンを用意する
- 「通常設定に戻す」操作で個別設定を解除し、その曜日の基本設定に戻す

## 25. 営業時間の変更と既存予約
- 予約が入っている日の営業時間も変更できる
- 既存予約に影響する可能性がある場合は警告を出し、院長の確認後に確定する
  - 例：「この日には既に2件の予約があります。営業時間を変更すると予約時間に影響する可能性があります。変更しますか？」
- 予約の自動キャンセル・自動変更はしない
- 影響がある場合、院長は患者へ電話で連絡する。システムからもメールアドレスがある患者へ通知する（変更後の営業時間と予約日時を記載）

## 26. UI 方針
- 患者側はスマートフォン中心で、シンプルかつ直感的にする
- 日時の選択は「日付 → 午前／午後 → 30分ごとの ○／×」の流れ
- 管理画面は PC 中心だが、スマートフォンでも最低限の操作ができるようにする

## 27. 個人情報とセキュリティ
- 扱う個人情報：氏名、電話番号、メールアドレス（任意）、施術希望内容。必要以上の情報は取得しない
- 認証・認可、CSRF 対策、バリデーション、SQL インジェクション対策、XSS 対策、予約管理 URL の推測防止などを適切に実装する

## 28. 実装方針
- 後から読んだ人がすぐに理解できるコードを重視する。過度な抽象化や不要なデザインパターンは避ける
- 予約の重複防止・認証・個人情報保護など、セキュリティとデータ整合性に関わる部分は妥協しない
- Laravel の標準機能をできるだけ使う
- DB 設計・API 設計・フロントエンド設計について、なぜその設計にしたのかを説明する
